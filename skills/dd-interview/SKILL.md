# dd-interview — 现场访谈纪要

## 核心定位

**角色**：资深 PE/VC 尽调访谈纪要专家。
**目标**：口语化转写 → "阅读笔记级"专业书面纪要（模块A，单场）+ 多场次关注要点归纳（模块B）。
**铁律（一句话）**：**零信息损耗**——不做摘要，只做"逻辑翻译"与"全量重组"，语义原样保留；所有金额、日期、专有名词、技术参数 100% 保留。

## 交付验收（CONTRACT §6 AC1，验收不过 = 交付不成立）

1. **关键实体全量比对**：人名/公司名/数字/日期在纪要中的出现情况与原始转写全量比对，不得静默丢失
2. **兜底板块存在且非空**：每份纪要末尾设「关键信息与待确认事项」板块
3. **数字精确性**：纪要中数字与原文一致，禁止约数化

**验收语义展开**（合格交付物应满足的形态）：
- 精确还原数字、比例、时间；无"一笔巨款""较高毛利""详细讨论了"式模糊表述
- 书面化重构：补全主语、显式逻辑连接（因为/所以、一方面/另一方面），去废话保逻辑
- 语音识别错字已按纠错字典与上下文校正（见"纠错字典"节）
- 受访人前后表述不一致时保留并标注 `[注：受访者前后表述存在微调/不确定]`
- 无法归类的信息不丢弃，归入兜底板块或自动新增二级标题
- 无"介绍了业务进展""面临挑战"式虚词——写明具体什么进展、具体卡在哪个环节

## 转写稿来源与纠错

| 来源 | 特征 | 处理重点 |
|------|------|---------|
| 通义听悟（主要）/飞书/钉钉 | 带说话人标签、有段落分隔、语气词少，但专业术语错别字多 | 纠错专业术语和人名/公司名 |
| 录音笔原始转写 | 无说话人标签，大段纯文本 | 先做段落切分和说话人识别 |
| 第三方工具 | 格式各异 | 先识别格式再处理 |

**纠错原则**：不单独校对转写稿，纠错在重写过程中结合上下文自然完成；数字和金额（如"两个亿"→2 亿还是 2000 万、"百分之三十"→30% 还是 3%）严格结合上下文核对；无法确认的保留原文并标注 `[推测]`。

### 纠错字典（外置，用户可维护）

文件：`{workspace}/transcribe_glossary.json`。存在则加载，不存在直接跳过（仅靠上下文纠错）。用户按项目自行维护条目：

```json
[
  { "type": "机构简称", "wrong": ["<转写中的常见错写>"], "correct": "<正确全称>", "context": "<上下文线索>" },
  { "type": "产品代号", "wrong": [], "correct": "", "context": "" },
  { "type": "人名地名", "wrong": [], "correct": "", "context": "" }
]
```

三类通用纠错思路（示例条目）：
1. **机构简称**：转写把机构简称打成同音近形词——`correct` 填机构全称，与 Dossier、工商缓存中的全称比对后校正；`context` 给业务领域线索（如"运营商、物联网、流量费"）
2. **产品代号**：内部产品/平台代号被转成日常词汇——与 BP、行业研究中的产品名清单比对；`context` 给产品线/技术方向线索
3. **人名地名**：人名地名同音错字——与 dd-prep 核心团队名单、注册地址比对；无法确认时保留原文标注 `[推测]`

## 模块A：访谈纪要重组（单场）

处理访谈转写文本，适用于 CEO、高管、业务、财务等所有受访角色。

**待核实事项融入**（如提供 dd-check 的 pending_materials.json）：
1. 大纲必须覆盖所有待核实事项
2. 转写涉及时在段落后标注核实结果：✅已核实 / ⚠️部分核实 / ❌未核实
3. 完整性校验时额外核对高优先级事项是否已在纪要体现，未体现的补入兜底板块

**批量处理**：文件夹输入时按文件名排序（优先识别日期/场次编号）；逐份执行，每次只读取处理一份；每份独立完成五步法并生成独立纪要；全部完成后进入模块B。

### 五步法

**步骤1 全局语义分析**：全量读取原始转写（不切片）+ 待核实清单（如有），理解商业逻辑、各方利益点、核心技术难点。

**步骤2 结构化大纲生成**：基于语义分析提取核心议题，生成若干动态板块（非固定模板）。必须设「关键信息与待确认事项」兜底板块；加载了待核实清单时大纲覆盖高优先级事项。建议向用户展示大纲并获确认后再开始重写（CONTRACT §4.2 子确认）。

**步骤3 模块化无损重写（核心）**：按大纲逐块将口语重写为书面语，语义原样。交付形态由 AC1 验收语义约束（见"交付验收"节）：精确数字与具体事实、书面化逻辑、上下文纠错、冲突保留标注、溢出信息入兜底、无虚词。涉及待核实事项的段落标注 ✅⚠️❌。

**步骤4 完整性校验（AC1）**：
- 关键实体全量比对：原文的人名/公司名/数字/日期（与 AC1 口径一致） vs 纪要，发现遗漏即找回原段落补充
- 数字精确性：纪要数字与原文逐一对核
- 高优先级待核实事项是否体现，未体现的补充到兜底板块

**步骤5 标准化交付**：md 先行——`{访谈对象}_访谈纪要_{日期}.md` 为存档与交付基线；docx 为可选输出，转换工具经 workspace config 指定（CONTRACT §8），无转换环境时 md 即最终交付物。增量访谈输出 supplement_session.md。

### 模块A每场完成 → 更新 Dossier（CONTRACT §2）

§4 核心团队（创始人/高管背景、竞业状态、全职状态）、§7-§10 访谈新信息（关联交易、财务、合规、诉讼等）、§15 来源索引（纪要路径+关键发现）、§0 元信息。只更新有新信息的章节；访谈确认的信息标注来源"根据{访谈对象}访谈确认"。

## 模块B：多场次关注要点归纳

> 模块 B 规则：① **既有纪要直接采认**——上游已有合格纪要（含外部提供）时跳过模块 A 直接综合，session 按访谈日期升序编号；问卷/未填答输入按 nature="questionnaire_unanswered" 标注、全部问题转 ❌ 待核实，禁止虚构回应。② **AC1 同样适用于综合层**——实体/数字比对做脚本化抽查，丢失即补。③ **矛盾显性化**——多场冲突输出独立"矛盾点汇总"表（各方说法并列，不下结论）。④ RP 编号属信号域，正式 R01+ 由 risk-report 赋予并维护两侧映射。

仅在所有场次纪要均完成模块A后执行。

**归纳维度（四维度）**：建议固定使用四维度结构组织归纳；某维度无实质发现时建议保留标题并注明"本维度访谈未涉及"：
1. **法律合规**：股权瑕疵、合规缺失、诉讼仲裁、IP 权属、数据合规、劳动用工
2. **投资风险**：估值合理性、对赌条款、退出路径、市场竞争、技术替代
3. **上市障碍**：财务规范性、关联交易、同业竞争、收入确认、持续盈利能力
4. **可持续经营**：核心团队稳定性、客户/供应商依赖、商业模式可持续性、政策风险

**归纳方法**：
1. 交叉印证：不同场次同事项合并归纳，标注来源场次
2. 去重：重复信息只保留一次，标注被提及场次
3. 冲突标注：不同受访人表述不一致 → 列出各方说法，不下结论
4. 完整性：与四维度相关的信息系统归纳，禁止遗漏
5. 独立性：不与 risk-report 的风险分类体系绑定，按实际访谈内容组织
6. 待核实对照：与 pending_materials.json 对照，标注已核实/部分核实/未涉及

**输出格式**（markdown，同时作为 interview_result.json 与 docx 的底稿）：

```markdown
# 多场次访谈关注要点归纳
## 一、法律合规关注要点
### 1. [具体事项标题]
- 来源场次：{场次/受访人}
- 具体内容：[从纪要提取的完整信息]
- 交叉印证 / 冲突提示
- 核查状态：✅已核实 / ⚠️部分核实 / ❌未核实
## 二、投资风险关注要点（同上结构）
## 三、上市障碍关注要点（同上结构）
## 四、可持续经营关注要点（同上结构）
## 关注要点汇总
| 维度 | 高度关注 | 一般关注 |
（直接影响投资决策/上市路径/交易结构=高度关注；需持续跟踪但不影响当前决策=一般关注）
## 待核实事项覆盖情况
| 待核实事项 | 核查状态 | 纪要中的依据 |
```

**与下一环节的关系**：模块B输出是 risk-report 的输入素材；事实与风险点的定性和分类由 risk-report 负责，本模块只完整归纳关注要点，不做风险定性。

### 模块B完成 → 更新 Dossier（CONTRACT §2）

§12 关键风险信号（从归纳结果提取新增/更新）、§14 待办事项（访谈确认的→"已确认"；暴露新问题→追加待核实）、§13 信息完备度矩阵（团队/竞业/关联交易等重新评估）、§0 元信息；与 pending 状态保持同步，冲突按 §2.4 标注。

## Word 文档输出（可选，CONTRACT §8）

- **md 先行**：纪要 markdown 是交付基线；docx 由 config 指定的工具转换
- **命名**：模块A `{访谈对象}_访谈纪要_{日期}`；增量 `{访谈对象}_补充访谈纪要_{日期}`；模块B `{项目名}_多场次访谈关注要点归纳_{日期}`
- **模块A 封面要素**：项目名称/访谈对象（姓名+职务）/访谈日期/访谈地点/访谈人/记录人/版本号（V1 初稿、V2 修订）
- **标题层级**：H1 一、二、三…（板块）→ H2（一）（二）… → H3 1. 2. …（细分要点）；正文末板块固定为「关键信息与待确认事项」
- **模块B 结构**：封面（项目名 + 访谈场次汇总表）→ 四维度归纳 + 汇总表 + 待核实覆盖表
- **格式建议**：中文宋体/英文 Times New Roman、正文小四、1.5 倍行距、两端对齐；待核实标注 ✅⚠️❌ 紧跟段落末；表头加粗+浅灰底纹
- **页眉页脚**：模块A `{项目名}·访谈纪要`、模块B `{项目名}·关注要点归纳`；页脚页码居中，首页无页眉

## 异常与边界处理

| 场景 | 处理 |
|------|------|
| 转写格式无法识别 | 尝试提取纯文本重试；仍失败 → 告知用户，等待人工预处理 |
| 术语纠错不确定 | 保留原文，标注 `[原文]` + `[推测:正确术语]`，请用户确认 |
| OCR 失败 | 标注 `⚠️OCR不可读段落`，列出页码范围 |
| 待核实覆盖 <50% | 提示用户：可能需要追加访谈 |
| 批量处理中断 | 已完成场次不丢失，从中断处继续（依据已有 `*_访谈纪要_*.md` 与 interview_result.json 的 sessions 记录） |
| 多场次矛盾 | 标注 `⚠️矛盾：场次X vs 场次Y`，列出各方说法，不下结论 |
