# 三版本对照验收协议（COMPARISON PROTOCOL）

> 目的：验证"精简流程（v0.3.0）产出的报告不差于直接让模型写，而且人更省事"。
> 这是 v0.3.0 减法收敛的收口验证：流程做的每一处保留，都应能说明它帮助了下方评价维度中的哪一项。
> 本协议是设计文档；执行需要模型宿主（全新会话代理），执行者**不得**事先阅读本文件（防污染，见"执行隔离"）。

## 1. 三臂设计

| 臂 | 内容 | 版本锚定 |
|---|------|---------|
| A 直接写 | 不加载任何技能，同一宿主模型收到同一组材料与同一句任务指令，直接产出报告草稿与待核实事项 | 无技能基线（指令全文见附录） |
| B 改动前流程 | v0.2.x 完整工作流（4 个人工审批检查点、逐项子确认、初筛卡 md+json 双文件） | git commit `cbd591c`（本轮改动前的实际基线：v0.2.2 之后还含知识库与文档收敛变更，比 tag v0.2.2 更准确的对照组），`git worktree add ../lrw-base-b cbd591c` 检出 |
| C 精简流程（改动后） | 本轮改动（入口分流、CP2 收口呈报、五问验收、默认交付三件、单文件初筛卡） | 运行开始前记录并固定待测提交号（tag 或 commit），运行期间该臂仓库不得再改动 |

**任务范围提示**：同一句任务指令（"基于以下材料出具法律风控报告草稿"）在各臂按各自版本的范围判断自行路由——B 会走完整尽调流程并在检查点等待审批，C 应识别为材料报告场景直接出草稿。路由本身是被测行为，主持者不得向执行者提示走哪条路径。

## 2. 材料组

- **统一材料目录**：开跑前由主持者构建一份三臂共用的干净材料目录（建议 `evals/comparison/materials_set1/`）：从 `examples/synthetic-demo/materials/` 物理拷贝，剔除 README、埋点答案、旧产出与任何评审材料——三臂都只拿到这个目录，A 臂"阅读全部材料"的指令因此安全。目录内容开跑后冻结。
- **组 1 埋点**：synthetic-demo 自带已知埋点（5-6 处应升为风险假设的信号 + 1 处专利材料缺口）。埋点清单由主持者持有，执行者与评审者初始不可见；评审结束后用于核对"重大问题识别"。
- **组 2（有具体未覆盖风险时再补）**：另一行业/轮次的合成材料（如 Pre-IPO 制造业），含至少 2 处**结论性缺口**（足以改变核心结论的材料缺失）与至少 1 处**多来源冲突**（工商与协议口径不一致），检验：材料不足时的区分处置（带限制继续 vs 暂缓）、冲突裁决后的表述、五问第 2/5 问。首次单组结果只支持该样本上的结论，不外推。
- 材料一律虚构或已脱敏；构造示例名时遵守虚构声明惯例（文件头注明"如有同名纯属巧合"）。

## 3. 控制变量

三臂保持一致：同一模型与宿主、同一工具权限（建议全部走手工采集模式，排除外部数据源差异）、同一任务措辞：

> "基于以下材料，就本投资项目出具法律风控报告草稿，并列出关键待核实事项。"

- A 臂只给这一句 + 材料路径。
- B/C 臂给同一句 + 材料路径，由工作流自行启动（B/C 的使用者交互按各自版本规则执行，交互本身是"使用负担"的测量对象）。
- 人工审批角色由同一测试审批人担任：按各臂规则放行检查点，放行动作照实计入"使用负担"（操作次数、确认次数），审批人**不向执行者泄露评审标准**。

## 4. 执行隔离（沿用回归测试纪律）

- 每臂由**全新会话代理**忠实执行：只见对应版本的技能与命令、统一材料目录，不见本协议、不见埋点清单、不见其他臂的产出。
- 每臂的执行产出原样留存（projects/{臂名}/），不做美化。

## 5. 盲评

- 评审者（具备 PE/VC 法律风控审阅能力）在**不知道版本来源**的情况下评审三份产出：去标识（统一改写文件名、路径、封面版本号为随机代号），呈报格式统一为"报告全文 + 待核实清单"。
- 评审者按第 6 节维度逐项记录证据（引用原文位置），不允许"总体感觉"式结论。
- **线索不等于成立**：发现风险信号不等于应当确认风险成立。评审应认可"准确识别线索并保留判断"（如"现有材料不足以确认权属清晰，也不足以认定侵权，建议取得 X 后再判断"）；把线索直接写成已确认风险、或为显得确定而硬下结论的，按判断可靠性缺陷记录，不得因表述笃定而加分。
- 评审者与执行者不得为同一会话。

## 6. 评价维度

| 维度 | 看什么 | 记录方式 |
|------|--------|---------|
| 重大问题识别 | 是否漏掉会改变决策的问题（对照埋点清单）；是否把埋点信号升级为风险判断 | 逐埋点核对：命中/遗漏/误报 |
| 判断可靠性 | 是否编造事实、误用依据、掩盖冲突或过度下结论；事实/公司陈述/推断是否分层；依据能否定位到材料 | 逐项列举，含原文位置 |
| 建议可执行性 | 是否知道下一步查什么、找谁、解决什么；是否落到交易条件 | 逐建议标注：可执行/空泛 |
| 人工修改成本 | 改到可以提交审阅需要多少实质修改 | 按处统计并分档：可暂缓 / 必须改 / 致命 |
| 使用负担 | 使用者需要多少操作、确认与额外阅读 | 从 project_log 与交互记录统计：确认次数、提问次数、需阅读文件数、收到文件数 |

## 7. 一票否决（不得被综合得分抵消）

- **重大误判**：编造事实、掩盖已呈现的冲突、或过度下结论导致方向性错误（如把"未提供"写成违规、把单方陈述写成已确认事实并据此定级）。
- **重大漏项**：遗漏任一埋点清单中"会改变决策"级别的问题。
- 任一臂触发即该臂单列"不通过"，即使其余维度得分最高。

## 8. 判定标准

- **C 相对 B**（减法没有减掉质量）：重大问题识别与判断可靠性不下降；确认/打断次数明显减少；初稿的人工修改成本不升高；变更摘要与默认交付三件是否让审阅更快定位问题。
- **C 相对 A**（流程相对裸模型有价值）：按识别准确性（对照埋点）、依据可靠性（可定位、不编造、冲突处理正确）、建议有效性（下一步动作可执行）、人工修改成本更低来判断；重大误判更少；且上述收益扣除使用负担后仍为正。**不因是否遵循本仓库的报告格式、章节结构或五问版式加分**——格式符合度不是质量证据。
- 未达判定标准的项目：回到 ROADMAP 记录，逐项决定是恢复原机制、调整实现，还是接受取舍并明示。

## 9. 记录产物

`evals/comparison/RUN_REPORT_{日期}.md`：三臂产出索引、盲评代号映射表（评审结束后解锁）、逐维度评分与证据、一票否决核对、判定结论与后续动作。主持者持有：埋点清单、代号映射、审批人交互日志。
